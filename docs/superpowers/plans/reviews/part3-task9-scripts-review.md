# Review: part 3 Task 9, Steps 1 to 4 (commit fe6f508e, perf measuring tools)

Reviewer: independent, read-only. `lib.test.mjs` run (arm64, nice): 21 passed. I also ran probe scripts against `lib.mjs` (results quoted below) and computed the baseline spread from `baseline/perf/*.json`.

## Verdicts

- Spec: PARTIAL. The plan's functions and flags are all there and the no-flag path of perf.mjs is unchanged. But the "any number worse than baseline, even inside budget, is a finding" rule is not met by `compareRuns`/`compare.mjs`: it can drop a row and it tolerates a lot.
- Quality: NEEDS FIXES before the numbers are trusted. The code is clean and tested where it was tested. The holes are in what is not tested.

## Critical (a regression can pass unseen)

C1. `lib.mjs` `compareRuns` (the loop, `if (!c) continue;`): it iterates only the keys and columns the CURRENT summary has. A measure or a whole column present in the baseline and absent from the current run is silently dropped, not printed. Probed: baseline with `idleFrames` and a `gpu phone` column, current without them: `compareRuns` returns only the one shared row (2 rows, phone column gone, `idleFrames` gone). A run that fails to measure `idleFrames`, or a viewport that crashed, therefore reads as clean. Fix: iterate the union of baseline and current keys and columns; for a baseline value with no current value emit a row `{ median: null, missing: true }`, print `MISSING` in the mark column and add a finding (`gpu phone: no value for X in the current runs`). Also have `judgeRows` treat `missing` as a finding. Test: baseline has key/column, current does not, expect a finding.

C2. `lib.mjs` `summarise` + `compareRuns`: a null or non-finite measure is dropped from that run (`summarise` L~118) and `n` is never compared. If two of three current runs have `null` for `dragGapMs` (a failed measure), the median is the one remaining run (probed: `{median:19, n:1}`), shown with no warning, and the table does not show `n` at all. Fix: carry `n` into the compare row (`baseN`, `n`), and flag `n < baseN` (or n less than the number of full runs) as a finding `MISSING RUNS (n of 3)`, print `n` in the table (e.g. `19 (n=1)`).

C3. `lib.mjs` `compareRuns` `worse: c.median > b.worst`: the tolerance is the whole baseline spread, which swallows real regressions and goes against the owner's rule. Baseline spread (median to worst) from the three baseline runs, which compare.mjs would accept as "not worse":
  - gpu desktop `startupLongTaskMs`: median 0, worst 345 (one outlier run). A current median of 200 ms (inside the 250 budget) passes. This is the case the rule exists for.
  - gpu desktop `mapFirstFrameMs`: median 575, worst 907 (+58 percent passes).
  - software phone `sliderToListMs`: 16 to 181 (11 times slower passes); `selectToAlbumMs` 18 to 77; software desktop `startupLongTaskMs` 57 to 122.
  - In the GPU columns frame gaps have 0 to 3 ms of headroom, so there the test is tight (1 frame step is flagged); in the software columns and the startup rows it is loose.
  The test file even asserts the loose case (`dragGapMs` median 33 against baseline median 20, `worse: false`). The report/commit say "a median inside the baseline's own spread is run to run noise": that is an assumption, and one outlier run widens the window for the other two. Fix (keep it simple, no invented epsilon): keep `WORSE` (median above every baseline run) and add a second tier `SLOWER` when `median > baseMedian` but not above worst, listed under Findings too (or as a separate "Slower than the baseline median, inside its spread" list that the write-up must explain). Print the delta (`+7`, `+35 %`) and the current min to max beside the median. That meets "any number worse is a finding" and keeps noise visible rather than hidden. If the owner wants a tolerance, it should be one named constant, shown in the output.

C4. `compare.mjs` L~85-90 (size lines): first-load JS and three.js are judged only against the budget (200 KB) and 0. Baseline is 190.5 KB: 199 KB is under budget and not a finding, but it is worse than baseline by the owner's rule. Same for `pageHtmlKb`/`pageHtml`, not compared at all. Fix: add findings `first-load JS X KB is above the baseline's largest (Y KB)` (baseline max over full runs); print the delta. (Report says the branch growth is to be explained separately; make the tool say so.)

## Important

I1. Exit code (your question 3). Recommend: exit 1 when there is any finding (OVER BUDGET, OVER YARDSTICK, WORSE/SLOWER, MISSING, size findings), exit 2 on usage error, exit 0 only on a clean run. For A/B pairs and exploratory use add `--no-fail` (or `--report-only`) so it is opt-out and the safe default gates. Note that `compare.mjs ... | tee` hides the status unless `set -o pipefail`; the runbook's `| tee` lines must be changed (`set -o pipefail`, or write to a file then `cat`). Where: `compare.mjs` last line: `process.exitCode = findings.length ? 1 : 0` (after the final console.log; the usage exits stay 2). Update the header comment ("Exit code: 0 whatever the findings").

I2. `perf.mjs` flags are not verified, only recorded. `effectsSeen` is written to the output but nothing stops the run when a flag did not take effect (header selector missing gives `null`, a stale build, a CSS rename). A glass A/B where nothing changed reads as "glass costs nothing". Fix: after `effectsSeen`, assert and add to `fails` (or exit 2): `--glass off` needs `headerBackdropFilter === 'none'`; `--glass on` needs it not `none` and `glassBlur` equal to the first value; `--names x` needs `namesOn === (x === 'on')`. For twinkle, `effectsSeen.twinkle` just echoes the global the script set, so it proves nothing: label it "unverified" in the console line and refuse (exit 2) until a real read-back exists (`window.__rmr?.twinkle`), per the TODO at `twinkleSwitch`. Otherwise a twinkle A/B against an app that ignores `__rmrTwinkle` gives two identical runs and a "no cost" result.

I3. Forcing perturbs the startup rows. `forceEffects` runs right after `goto('/')` (perf.mjs measure, after `await page.goto`), inside the window that `startupLongTaskMs` (a long-task observer from load, read after the 4 s wait) and `mapFirstFrameMs` cover. Setting four inherited custom properties on `<html>` invalidates style for the whole tree and, with the blur changing, repaints the header and panels: one extra style recalc (and a possible long task) at the worst moment. The same on the two `/map` loads (before `waitForFunction`), harmless there because the 1.5 s settle comes before any measured step. The names init script and the effects readback are harmless (the init script is a localStorage write before load; `effectsSeen` is called after the budget rows). Consequence: with `--glass`, startup rows are not like for like with a no-flag run; step 8's "everything off against the baseline" compares those rows. Fix, either: (a) print and document that startup/first-frame rows of a `--glass` run are not comparable, and have compare.mjs skip `startupLongTaskMs`/`mapFirstFrameMs`/`searchUsableMs` as judged rows when `effects.glass` is set; or (b) apply the glass override before first paint (an init script that adds a `<style>:root{...}` on `DOMContentLoaded`... still perturbs) so the cleaner option is (a). Note `--glass on` on desktop writes values identical to the stylesheet's, so it is a restyle only; `--glass off` also changes `.map-tip` while `.map-tip` is still in the glass rule of `wt/trifid-part3` (report mentions it).

I4. `compare.mjs` ignores what the JSON says about how the run was made. `open` ('whole'/'app'), `effects` (only with flags) are read by nobody; `--no-gas`, `--gas-lite`, `--allow-software-gpu` are not recorded in the JSON at all. A current directory that holds a leftover glass-off file from a forced run would be averaged into the median of three with no warning (only the count 3 is checked). Fix: in `perf.mjs` write `flags: { noGas, gasLite, allowSoftwareGpu }` only when any is set (keeps no-flag JSON identical); in `compare.mjs` print per file `open`/`effects`/`flags` when present and add a size finding when the files of one side disagree or when a current side has any `effects`/`flags` ("not the site as a visitor gets it") unless `--no-fail`/`--allow-flags`.

I5. Runbook, step 1 and `keep()`: `keep` copies `ls -t scripts/perf/out/perf-*.json | head -1`. If a run dies before writing its JSON, `keep` silently copies the PREVIOUS run's file under the new name: a duplicate run counts as a fresh one and the median of three is not three. Also a run that breaches a budget exits 1 (it writes the JSON first, fine) but the loops do not tell the two cases apart. Fix: `before=$(ls scripts/perf/out | wc -l)` check, or empty `scripts/perf/out` before each run and fail `keep` if no file is there (`f=$(ls -t scripts/perf/out/perf-*.json 2>/dev/null | head -1); [ -n "$f" ] || { echo "no JSON"; return 1; }; mv "$f" "$A/$1.json"`). Same in section 6.

I6. Runbook A/B design (steps 6 to 8): one run per side, always `on` then `off` (order and heat bias), "within 5 ms run once more". With n=1 on each side the compare rule is "above that one run", so anything is flagged or nothing is. Fix: interleave `on off on off on off` into `glass-<col>/on/perf-runN.json` and `.../off/perf-runN.json` (the names compare.mjs reads) and compare the two folders; the tool already supports directories. Keep the 5 ms heuristic out.

I7. `fillBaseline` (your question 2): it cannot mix modes or viewports: `summarise` keys on `${mode} ${vp}`, extras only fill `deepDragGapMs`/`deepMorphGapMs`, only where the baseline folder has no entry for that exact column and key, and each key's n comes from one set only. Verified against the data: extras are all `gpu` (desktop, phone, desktop2x); the baseline folder's dpr2 files already hold deep rows for `gpu desktop2x`, which win. Two gaps: (a) `gpu desktop2x` of the extras is ignored but the extra files' other rows are not, correct; (b) provenance is not stated per row: the table gives no sign that a baseline deep row came from a different file set and a different day of measuring. Fix: mark such rows `(extra)` in the table, and add a test with a software extra row proving it can fill `software desktop` only if the folder had none (today it would; that is a risk only if someone passes a software extra file: restrict to `where.startsWith('gpu ')` or a stated column list).

## Minor

M1. `summarise` throws `TypeError: Cannot read properties of null (reading 'mode')` on a null row in `rows` (probed). It is loud (stack trace, exit 1) but unfriendly and would be read as a tool bug. Fix: skip null rows with a counted warning, or validate in `readRun` (`compare.mjs` L~38) with a file name in the message. Even counts: median of 2 or 4 averages the middle two (probed 3 values: correct, and the code is right for even); not tested.

M2. `glassVars` takes "first value is glass, last is solid" by position. Correct against `wt/trifid-part3` `globals.css` (lines 24, 36-41 and the three solid blocks at 50-52, which match the report's `off` values exactly). But it relies on file order: a later block that sets `--glass-blur` to a third value would silently become "solid". Fix: assert the last `--glass-blur` is `none` and the last colours have alpha 1 (rgba(..., 1)), else throw. Also it reads `src/app/globals.css` from the working tree while the build under test is `.next`: a stale build gives a wrong A/B; the `effectsSeen.glassBlur` of `on` runs partly guards this (see I2).

M3. `--glass` with no tokens exits 2 (your question 4): good, keep it. A silent no-op would produce an A/B of nothing. Say so in the message ("measure a build with the glass tokens").

M4. No-flag path of perf.mjs (your question 4): confirmed unchanged from the diff. `onOff` returns null with no flag; `presetEffects`/`forceEffects` return before doing anything (two extra awaits of resolved promises before `newPage` and before `waitForFunction`, no timer, no init script, no style, no wait); `ANY_EFFECT` false so no extra JSON key or console line; defaults of the existing flags untouched. "Byte for byte the old path" holds for output and JSON; timing differs by microtasks only. `forceEffects` is after all three loads (L313, L361, L465 equivalents).

M5. `effectsSeen` reads only `header.top` for glass. Panels, album, zoom buttons, `.map-names` are not read back; one more property read each (`.panel`, `.album`) would prove the four custom properties reached them.

M6. Runbook step 6 asymmetry: new runs also do the opening-view flow (second context, extra minute of load), old runs (`--open whole`) do not, so the machine is warmer before each new run than before each old one. If the order is old then new inside one loop, the new build always runs hotter. Alternate the order per iteration (old,new / new,old / old,new) or add the same sleep. `--no-gas` for the old build and not for the new one is right (the new run must wait for gas, as a visitor does); keep it.

M7. Runbook completeness (your question 7): it has same session, in turn, mains check (`pmset`), arm64 check, no `nice`, median of three, `--open whole` for the old, and the deep extras. Missing: record `git rev-parse HEAD` of both trees and the `uptime`/`pmset` output into `$A` so a result can be tied to a build; `set -o pipefail` for the `tee` lines (I1); say that `perf` exits 1 on a budget breach by design and the loops must keep going; the old tree's `budgets.json` is the old one (compare.mjs uses the new tree's, which is what you want, say so); the plan's check that the new `perf.mjs` starts against the old tree is marked "not tried": run it once (`--no-gas --open whole --mode gpu --viewport phone`) before the real loop.

M8. Direction check (your question 1): every key in `COMPARE_KEYS` is lower-is-better (times, gaps, long-task ms, `idleFrames`, `idleLongTasks`, `gasShownMs`, `mapFirstFrameMs`), so a single `>` is right. Median of three correct for odd and even counts (probed 3 values, code path for even is the standard average). Ties are not worse (`>` strict): fine at integer ms, but note frame gaps move in about 16.7 ms steps so a tie is common in GPU columns. "n/a" is printed only when `baseline[where][key]` is missing (`compareRuns` null branch), which is correct, but a baseline key that exists only because it was filled from extras is not marked (I7). `judgeRows` does not mark `worse` for an n/a row: correct.

## Tests (your question 6)

The 10 new tests prove: glassVars on/off/invalid (synthetic CSS only), median/best/worst for 3 runs, WORSE above worst and idleFrames from 0, columns apart, n/a rows, opening rows, fillBaseline order and no mutation, judgeRows marks and yardsticks.

They do not prove, and need:
1. A baseline row/column/key missing from the current run is reported (C1): no test; the current code fails it.
2. `n` fewer than expected / null in some runs (C2).
3. Median for an even count (2 or 4 runs) and for a single run; a null row in `rows`.
4. The tie: `median === baseWorst` is not WORSE; and the new SLOWER tier if C3 is adopted.
5. fillBaseline with a software extra row, and one key filled while the other is present (partial fill).
6. `compare.mjs` itself has no test: `isDpr2File`/`rowsOf` filtering, sorting, the three-run size finding, the JS size findings, usage errors and exit codes. Move the logic into `lib.mjs` (it already moved `judgeRows`) or add a small spawn test over two fixtures.
7. `glassVars` against the real `globals.css` (a test that reads `src/app/globals.css` once the tokens exist, in the style of `glass.test.ts`): the synthetic CSS passes whatever the real file looks like.
8. perf.mjs flag parsing and the no-flag JSON shape: no test; not covered by smoke either.
